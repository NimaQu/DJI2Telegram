# 音频连续性修复与 16 kHz 验证（2026-09-10）

## 范围

测试实例 `100.74.210.88` 仅做读取，未部署、重启或修改配置。它的旧版 `448d44f` 日志表明，约 134 秒通话中，客户端到模块方向溢出丢弃 30 帧，并补充了 353 个静音周期；启动等待包含在静音统计中，不能直接解释为讲话断续时长。

修改和硬件实验使用 `192.168.88.177`。未拨出真实电话、刷写固件或修改模块持久配置。临时音频实验后恢复网关服务。

## 修复

- 客户端播放队列先积累 60 ms，运行中断流后重新积累，目标最多 120 ms，容量上限 400 ms。
- ALSA 采集和播放使用独立线程；播放使用单调时钟的绝对 20 ms 截止时间，避免按每次写入耗时累积漂移或过快消耗队列。
- ALSA 启动预填充；欠载后重试原始数据，短写继续提交剩余部分，重试有上限。
- 退出时先等待音频线程结束再关闭设备，防止关闭仍在执行 I/O 的句柄。
- 增加接收间隔、供给音频时长、运行中缓冲耗尽、启动/重新缓冲补静音、实际 ALSA 格式与恢复失败统计。
- 保留现有 PCM16、8 kHz、单声道、20 ms WebSocket 协议。

## 验证结果与限制

自动化测试覆盖抖动/分批传输、缓冲上限、欠载与短写、事件循环忙时音频线程继续运行，以及安全关闭。模拟网络交替以 260/140 ms 间隔送达每包 200 ms 音频，新的队列比原 200 ms FIFO 显著减少播放空洞，且没有溢出丢帧。

在原服务器进行 16 秒硬件实验，按 120/80 ms 交替间隔输入每包 100 ms 音频。800 帧均从队列送出，无溢出丢帧、无未恢复写入错误；播放线程没有时钟重同步。启动预填充之外，运行中出现 3 个重新缓冲静音周期。

**该实验仍出现 802 次 ALSA 欠载恢复，不能据此宣称真实音质已经修复。** 为区分应用问题，进一步绕过 bridge 和 Python，使用系统 `aplay`，播放 2 秒、8 kHz 的零采样数据；它约 0.063 秒便退出，并报告多次 underrun。这说明此测试主机的 USB/ALSA 路径还有独立异常，不能拿它作为正常实机音质基准。没有在另一个实例上复现这个实验，也不能把此硬件异常直接归因于另一实例。

`snd_usb_audio.lowlatency` 为只读运行时参数，临时切换尝试被内核拒绝，未改变其原值；没有卸载驱动或改动开机参数。硬件测试不能替代客户端、蜂窝网络和真实对端的通话复测。

## 16 kHz

对原服务器的 `hw:0,0` 分别请求 16 kHz 录音和播放，再读取 ALSA 实际参数：两者实际采样率均为 **8000 Hz**。USB 描述符也只公布 8000 Hz。

模块内核为 3.18.44；当前 USB functions 为 `diag,serial,ecm,ffs,audio`。`f_audio` 只暴露 `audio_enable` 等属性；`f_uac2_func` 没有采样率配置属性，没有发现可用的 USB gadget configfs 实例。随项目提供的语音 helper 也没有采样率命令行选项。

因此当前已验证的 USB 音频通路不能直接配置为原生 16 kHz。仅修改 App 或 bridge 的声明会产生重采样，不会增加真实语音带宽。本次保持 8 kHz；进一步的宽带支持需要模块固件/USB gadget 与 DSP 语音路由层面的独立开发和验证。
